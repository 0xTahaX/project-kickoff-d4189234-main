# معماری دارا — فاز ۱

## معماری فعلی و دلیل مهاجرت

نسخهٔ اولیه رابط HTML/CSS/JavaScript بدون ابزار ساخت داشت و سرور Express/JavaScript با SQLite احراز هویت را مدیریت می‌کرد. بعد از مهاجرت به TypeScript، احراز هویت برای مدتی از رابط جدا شده بود؛ اکنون API حساب کاربری با نام کاربری و گذرواژه و داشبورد مهمان هر دو فعال‌اند.

برای تثبیت پایهٔ MVP، به‌جای ادامهٔ رشد فایل‌های اسکریپتِ سراسری، پشتهٔ React/TypeScript/Vite برای رابط و Express/TypeScript/Prisma/PostgreSQL برای API انتخاب شد. Prisma 7 با adapter رسمی PostgreSQL و client تولیدشده در سورس استفاده می‌شود. این تصمیم، نصب وابستگی و راه‌اندازی PostgreSQL می‌خواهد و یک مهاجرت تدریجی است؛ به همین علت رابط داشبورد موجود در مسیر `/legacy/` حفظ می‌شود و جایگزینی رابط آن به فاز بعدی موکول است.

## ساختار

- `apps/web`: برنامهٔ React و TypeScript، مسیریابی، Vite و CSS؛ پس از redirect، رابط داشبورد و auth در `/legacy/` اجرا می‌شود.
- `apps/api`: سرور Express و TypeScript، API احراز هویت و دفتر مالی، ایمیل SMTP برای بازیابی گذرواژه، endpoint سلامت و Prisma.
- `apps/api/prisma`: مدل PostgreSQL و migrationهای نسخه‌بندی‌شده.
- `apps/web/public/legacy`: نسخهٔ فعلی داشبورد برای حفظ رفتار موجود در دورهٔ مهاجرت.
- `docs`: معماری، تصمیم‌ها، راه‌اندازی دیتابیس و محدودیت‌های فاز.

API و وب در توسعه روی دو پورت هستند؛ Vite مسیر `/api` را به API پراکسی می‌کند. در استقرار Render، API خروجی build وب و داشبورد قدیمی را از همان origin سرو می‌کند تا کوکی نشست first-party باشد. `render.yaml` ساخت، اجرای migration و health check را تعریف می‌کند.

## مرزهای دامنه

- **احراز هویت و پروفایل:** ثبت‌نام و ورود با نام کاربری و گذرواژه انجام می‌شود؛ نام کاربری پیش از ذخیره و جست‌وجو یکسان‌سازی و کوچک‌حرف می‌شود تا بزرگی/کوچکی حرف و شکل‌های عربی «ی/ک» حساب تکراری نسازند. ثبت‌نام بلافاصله نشست می‌سازد و به SMTP یا ایمیل نیازی ندارد. ایمیل اختیاری فقط برای بازیابی گذرواژه استفاده می‌شود و تأیید نمی‌شود. ورود Google در آینده اضافه می‌شود؛ به همین دلیل ستون‌های `email`، `password_hash` و `password_salt` در دیتابیس اختیاری‌اند تا حساب ساخته‌شده با Google بدون گذرواژه ممکن باشد. تغییر/حذف حساب و بازیابی یا تغییر گذرواژه، خروج و فهرست نشست‌ها فعال‌اند. cookie نشست HttpOnly/Secure است و توکن نشست و reset فقط به شکل hash ذخیره می‌شوند.
- **ترجیحات مالی:** زبان و ارز پیش‌فرض در پروفایل کاربر؛ ارز با کد ISO 4217.
- **حساب‌ها، دسته‌ها و تراکنش‌ها:** دفتر تراکنش/account/category در PostgreSQL با شناسهٔ مالک ذخیره می‌شود؛ guardهای API تمام پرس‌وجوها را به کاربر واردشده محدود می‌کنند.
- **بودجه و سایر داده‌های رابط:** بودجه/هدف/پرداخت تکرارشوندهٔ داشبورد، دارایی‌ها، کیف‌پول/ژورنال، ترجیحات و یادآورها در JSONB جدول `user_workspace` و با کلید مجاز و مالک کاربر ذخیره و بین دستگاه‌ها sync می‌شوند؛ تراکنش‌ها جداگانه در دفتر رابطه‌ای ذخیره می‌شوند و داخل snapshot داشبورد تکرار نمی‌شوند. سقف هر بخش ۵۱۲ KiB است. localStorage حساب فقط cache است، فضای مهمان جداست و خودکار به حساب منتقل نمی‌شود.
- **بودجه، هدف، پرداخت تکرارشونده و بدهی:** مدل‌سازی اولیه و وابسته به کاربر؛ رابط/API در فاز بعدی.
- **دارایی و ارزش خالص:** دفتر محلی دارای دارایی، تاریخچهٔ ارزش‌گذاری، بدهی، نرخ دستی ارز، ownership و قواعد جلوگیری از دوباره‌شماری.
- **سبد سرمایه‌گذاری:** دفتر رویداد محلی با lotهای FIFO، فروش جزئی، هزینه‌ها، درآمد نقدی، انتقال lot و بازده ساده؛ بدون اتصال به بازار.
- **بازارها:** endpoint عمومی قیمت Iran Market Data فقط از API سرور خوانده می‌شود؛ UI به JSON سرور متصل است و داده را از منبع بیرونی مستقیم نمی‌خواند. یک cache کوتاه‌عمر حافظه‌ای آخرین پاسخ معتبر را نگه می‌دارد؛ مدل دیتابیس یا تاریخچهٔ دائمی افزوده نشده است.
- **کیف پول زنجیره‌ای:** provider مستقل خواندن Ethereum Mainnet از Blockscout، snapshot موجودی ETH و ERC-20، ۵۰ تراکنش و انتقال اخیر و dedupe با شناسهٔ transaction/log را ارائه می‌کند. مرور/طبقه‌بندی تراکنش‌ها و ثبت نشانی در localStorage است؛ صفحه‌بندی ادامه‌دار و تبدیل تراکنش به دفتر حسابداری وجود ندارد.
- **ژورنال معاملات:** ثبت دستی معامله و خروج جزئی در localStorage؛ هزینهٔ ورود میان خروج‌ها تخصیص می‌یابد و سود تحقق‌یافته/تحقق‌نیافته تفکیک می‌شود. ارزهای متفاوت باید جدا گزارش شوند؛ معیار افت سرمایه فقط با سرمایهٔ آغازین مشخص معتبر است.
- **دستیار مالی:** ترجیحات کاربر در localStorage ذخیره می‌شود؛ پاسخ محلی فقط تحلیل‌های قطعی و مشخص‌شده را از اطلاعات همان دستگاه نشان می‌دهد. provider زبانی متصل نیست و هیچ پاسخ AI واقعی یا توصیهٔ سرمایه‌گذاری تولید نمی‌شود.
- **حریم خصوصی:** داده‌های guest فقط در localStorage همان مرورگر می‌مانند؛ دادهٔ حساب با userId در PostgreSQL جدا می‌شود. payload فضای کاری از طریق API محدوداندازه و بدون کلیدهای دلخواه پذیرفته می‌شود.

## امنیت و داده

- migration نام کاربری/ورود و فضای کاری باید روی دیتابیس مقصد از طریق `npm run db:migrate` اجرا شود؛ migration روی دیتابیس واقعی این repository به‌صورت خودکار از این محیط انجام نشده است.
- حساب/تراکنش‌ها دارای روابط مالکیت مرکب هستند. بخش JSONB هم فقط از API احراز هویت‌شده و userId نشست جاری قابل‌خواندن/نوشتن است.
- API بازار فید `latest-toman.json` را از Iran Market Data می‌خواند؛ پاسخ پنج‌دقیقه cache، timeout ده‌ثانیه‌ای و سقف اندازهٔ پاسخ دارد. وضعیت stale از زمان قیمت منبع یا خطای دریافت ساخته می‌شود. اگر fetch شکست بخورد، فقط آخرین پاسخ معتبر همان process با برچسب stale ارائه می‌شود؛ پس از restart، در نبود منبع قیمت در دسترس نیست.
- endpoint کیف‌پول فقط خواندن است و بدون API key به `eth.blockscout.com/api/v2` وصل می‌شود؛ timeout ده‌ثانیه‌ای، cache شصت‌ثانیه‌ای و محدودیت درخواست دارد. snapshot ناقص هشدار می‌دهد؛ تاریخچه در هر پاسخ تا ۵۰ رکورد محدود است. این endpoint مالکیت آدرس را اثبات نمی‌کند و اطلاعات را در دیتابیس/حساب کاربری ذخیره نمی‌کند.
- provider chain فقط قرارداد مشترک normalizing را دارد؛ provider-specific response mapping در `apps/api/src/blockchain/ethereum-provider.ts` است. دسترسی به آدرس عمومی و طبقه‌بندی محلی، هیچ‌کدام تراکنش را به حسابداری شخصی وارد نمی‌کنند.
- مقادیر بازار در حافظهٔ API هستند و دیتابیس برای فاز نمایش قیمت استفاده نمی‌شود. هیچ API key به Frontend ارسال نمی‌شود.
- در حالت مهمان، wallet و journal در localStorage همان مرورگر هستند؛ پس از ورود، snapshot آن‌ها در فضای کاری حساب sync می‌شود. private key/seed یا credential صرافی جمع‌آوری نمی‌شوند. قیمت‌گذاری معامله دستی است؛ هیچ order یا اتصال صرافی، smart-contract action، اتوماسیون درآمد/هزینه، و محاسبهٔ TWR/MWR وجود ندارد.
- مبلغ‌ها در طرح PostgreSQL از `Decimal(20, 6)` استفاده می‌کنند؛ محاسبهٔ authoritative در API مالی هنوز وجود ندارد.
- شناسهٔ ارز در ترجیحات ISO 4217 است و دقت اعشاری باید برای هر ارز رعایت شود.
- زمان‌ها در دیتابیس با `timestamptz` و UTC ثبت می‌شوند.
- هیچ payload حساس مالی در log نوشته نمی‌شود. در این فاز logging ساختاریافتهٔ عملیاتی و سامانهٔ پایش هنوز تنظیم نشده است.

## فاز ۵ — دستیار، یادآورها و مدیریت داده

- `apps/web/public/legacy/phase5-core.js` منطق خالص ترجیحات، اعتبارسنجی و پیش‌نمایش CSV، خروجی CSV تراکنش و محاسبهٔ یادآورهای محلی را دارد؛ فایل‌های بارگذاری‌شده اجرا نمی‌شوند. محدودیت CSV یک مگابایت و ۵۰۰۰ ردیف است. پس از تأیید پیش‌نمایش، حالت حساب همهٔ تراکنش‌های واردشده را در یک درخواست اتمیک به دفتر PostgreSQL می‌فرستد؛ حالت مهمان فقط در مرورگر ذخیره می‌کند. خروجی CSV در برابر formula injection با پیشوندگذاری محافظت می‌شود.
- `phase5-ui.js` نمای ترجیحات/تحلیل محلی/یادآورها/ورود و خروج داده را به صفحات موجود متصل می‌کند. ترجیحات و وضعیت خواندن یادآورها در دو کلید localStorage جدا هستند. اعلان‌ها deduplicate می‌شوند و فقط هنگام بازشدن صفحه محاسبه می‌شوند؛ scheduler، push، ایمیل و پیامک نداریم.
- سرویس TypeScript در `apps/api/src/assistant/assistant.ts` یک مرز provider مستقل، بررسی مجوز/مالکیت/رضایت، اعتبارسنجی context/output و محدودیت مصرف درون‌حافظه‌ای فراهم می‌کند. در نسخهٔ حاضر، احراز هویت و منبع مجاز داده به سرویس متصل نیست و provider پیکربندی نشده است؛ تنها route عمومی وضعیت تنظیمات را اعلام می‌کند. هیچ پاسخ AI یا تحلیل ساختگی تولید نمی‌شود و تیک رضایت ذخیره‌شده، به‌تنهایی باعث ارسال اطلاعات نمی‌شود.
- تحلیل دستیار در حال حاضر فقط جمع درآمد/هزینه، بیشترین هزینه‌ها و جمع بودجه را از دفتر همین دستگاه با کد قطعی محاسبه می‌کند؛ این تحلیل علت تغییرات را استنباط نمی‌کند و توصیهٔ شخصی سرمایه‌گذاری نیست. دادهٔ context فقط پس از اتصال احراز هویت، منبع server-side مالکیت‌دار، محاسبات قطعی و اخذ رضایت قابل ارسال خواهد بود.
- «پاک‌سازی داده‌های همین دستگاه» فقط کلیدهای Dara در localStorage مرورگر را حذف می‌کند. این عملیات حذف حساب/نشست سروری نیست. CSV تراکنش و JSON backup فقط در مرورگر ساخته می‌شوند و فایل خروجی باید امن نگه‌داری شود.
- خانواده/حساب مشترک، مالیات، بیمه، بازنشستگی، حذف حساب سروری، مدیریت نشست، گزارش زمان‌بندی‌شده و اعلان خارجی به علت نبود مدل مجوز/زیرساخت لازم به تعویق افتاده‌اند.

## تصمیم‌های مهاجرت

1. پشتهٔ فعلی در فایل‌های ریشه حفظ شده و به `apps/web/public/legacy` کپی می‌شود تا در طول انتقال قابل اجرا بماند.
2. دیتابیس قدیمی SQLite و داده‌های کاربران آن خودکار منتقل یا حذف نمی‌شوند.
3. تا زمان تنظیم `DATABASE_URL`، API و migrationها قابل build/validate هستند، اما اتصال به پایگاه‌دادهٔ جدید اجراشدنی نیست.
4. رابط وب فعلی داشبورد مهمان را نمایش می‌دهد؛ مدیریت اطلاعات مالی همچنان در رابط legacy و localStorage است.
5. پیش از تولید عمومی: PostgreSQL پشتیبان‌گیری‌شده، TLS، logging/monitoring، بررسی حقوقی و بازبینی امنیتی عملیاتی لازم‌اند.
